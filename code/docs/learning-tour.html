基础 · 地基

① 登录 / 鉴权（Sa-Token）

一切的起点。为什么后面每个接口都要带 satoken？就是这一步发的。

业务含义

操作工在 PDA/电脑上登录，系统校验账号密码，发一个 token。之后每次点按钮，浏览器自动把 token 放进请求头，后端靠它知道“你是谁、有什么角色”，没带或过期就拦回去。这就是 Sa-Token 干的活。

页面：mes-tws-ui/src/views/login/Login.vue 点「登录」
→ axios：src/api/auth.js 的 loginApi({username,password}) → POST /api/auth/login
→ 返回的 token 存 localStorage.satoken，src/api/request.js 拦截器自动给后续请求加 satoken 头
→ Controller：AuthController @RequestMapping("/api/auth") → login(LoginDTO)
→ Service：AuthService.login()：查 sys_user → BCrypt 校验密码 → 校验 status==1 → StpUtil.login(userId) 签发 token
→ 返回 token / userId / username / roleCode

鉴权怎么生效（两个开关）

登录拦截mes-server/.../config/WebConfig.java 注册 SaInterceptor，拦截所有 /api/**，放行 /api/auth/login。没登录 → 401。
角色拦截StpInterfaceImpl.getRoleList() 从 sys_user.role_code 取角色；接口上写 @SaCheckRole("admin") 才允许（如物料的保存/删除）。无权限 → 403。
用户表sys_user：id / username / password(BCrypt密文) / nick_name / role_code / status
sequenceDiagram participant U as 登录页 Login.vue participant A as AuthController participant S as AuthService participant DB as sys_user表 U->>A: POST /api/auth/login {username,password} A->>S: login() S->>DB: 查用户 + BCrypt校验 DB-->>S: 用户记录 S->>S: StpUtil.login(userId) 签发token S-->>A: {token, roleCode...} A-->>U: Result(token) Note over U: 存localStorage.satoken
后续请求自动带satoken头

学完这一层你该记住：token 是后面所有接口的“门票”；WebConfig 管“有没有登录”，@SaCheckRole 管“有没有权限”。

基础 · 模板

② 物料 CRUD（标准三层模板）

这是全项目 CRUD 的“母版”。后面工艺路线、字典、客户……全是复制它的套路。吃透这一个，其余一看就懂。

页面：mes-tws-ui/src/views/base/Material.vue
→ axios：src/api/material.js → GET /api/material/page（查询）、POST /api/material/save（新增/编辑）、DELETE /api/material/{id}（删除）

业务 · 模板

③ 工艺路线版本 + 快照

工艺路线 = 这个产品要过哪些工序、每道工序要防什么呆。它是“模板”，真正干活的是它被复制到工单里的“快照”。

业务含义

做一只 TWS 耳机，要先烧录→RF→组装→声学→左右耳耦合→盒段→三码绑定→老化→FCT→外观→包装。这条“工序清单 + 每道工序的防呆规则”就是工艺路线。它会升版（今天 8 道工序，明天改成 9 道）。但已经在做的工单，绝不能因为它升版就跟着变——所以建工单时要拍快照，把当时的工序和规则原样复制一份。

页面：mes-tws-ui/src/views/base/Routing.vue
→ axios：GET /api/routing/page（列表）、POST /api/routing/save（存草稿）、POST /api/routing/{id}/publish（发布）、复制新版本=取数据改名再 save
→ Controller：MdRoutingController @RequestMapping("/api/routing")
→ Service：MdRoutingService.save() / publish() / releasedList()
→ 表：md_routing（路线头）、md_routing_operation（路线工序，含 check_rules JSON）、快照plan_wo_operation
md_routingrouting_code, version(整数递增), status(0停用/1草稿/2已发布)，唯一键 (routing_code, version)
md_routing_operationrouting_id, seq(工序顺序), operation_code, check_rules(防呆规则JSON)
plan_wo_operation（快照）work_order_id, seq, operation_code, operation_name, operation_type, check_rules —— 建工单时从上面复制而来，之后与路线脱钩
flowchart LR A[md_routing 模板
version=2 已发布] -->|WorkOrderService.create 复制| B[plan_wo_operation 快照
绑定到某个工单] A -.->|路线升版到 v3| C[md_routing version=3] B -.->|快照不变| D[在制工单按 v2 工序走]
为什么叫“快照”是核心设计？ 客户审厂要求“证明你当时就是这么生产的”。路线升版不影响在制工单，plan_wo_operation 永远封存“建单那一刻”的工艺——这就是追溯的证据链起点。

学完这一层你该记住：路线是“活模板”（会升版），快照是“死证据”（建单时固化）。过站时查的是快照 plan_wo_operation，不是路线主数据。

业务 · 核心

④ 工单状态机 + 乐观锁

工单 = “这一批要做 5000 只耳机”的生产令。它有一套严格的状态流转（状态机），还要防两个计划员同时改同一张单（乐观锁）。

业务含义

工单生命周期：CREATED 新建 → RELEASED 下达 → IN_PROGRESS 开工 → PAUSED 暂停 → IN_PROGRESS 恢复 → COMPLETED 完工 → CLOSED 关闭。不能从“新建”直接跳“完工”——这就是状态机的护栏。两个计划员同时点“下达”同一张单，后者的修改不能把前者的覆盖掉——这就是乐观锁。

页面：mes-tws-ui/src/views/plan/WorkOrder.vue
→ axios：GET /api/wo/page、POST /api/wo/create、POST /api/wo/{id}/{action}（action=release/start/pause/resume/complete/close）
→ Controller：WorkOrderController @RequestMapping("/api/wo")
→ Service：WorkOrderService.create()（同时拍路线快照！）/ transition(id, action)
→ 表：plan_work_order

状态机：一张“允许迁移表”

// WorkOrderService 里的静态迁移表 —— 加一种流转只加一行
TRANSITIONS = Map.of(
  "release",  List.of(CREATED,     RELEASED),
  "start",    List.of(RELEASED,    IN_PROGRESS),
  "pause",    List.of(IN_PROGRESS, PAUSED),
  "resume",   List.of(PAUSED,      IN_PROGRESS),

  "close",    List.of(COMPLETED,    CLOSED)

// transition() 先查当前状态是否匹配“前置”，不匹配就抛“不能执行”

乐观锁：用版本号代替数据库锁

// 实体上挂 @Version，配置类注册拦截器
@TableName("plan_work_order")
public class PlanWorkOrder {
  private String woNo;
  private Long routingId, routingVersion;  // 快照时的路线版本
  private String status;                    // CREATED/RELEASED/...
  @Version private Integer version;         // 乐观锁，默认 0
}
// MesInfraConfig 注册 OptimisticLockerInnerInterceptor
// update 时自动带 WHERE version=? 并在成功时 version+1
// 两人并发改同一单 → 后者更新 0 行 → 抛“请刷新重试”

学完这一层你该记住：① 建工单那一刻就调用路线快照（回到第③步）；② 状态机用“迁移表”实现，非法跳转直接拦；③ 乐观锁用 version 字段，避免长事务锁表。

核心 · 重中之重

⑤ 过站引擎八规则链（核心！）

“过站”= 一个 SN 在某个工位扫一下、过了这道工序。这是整个 MES 最值钱的一段——后面面试八成围绕它。它要用 8 条防呆规则把“跳站/重过/混料/漏测”全拦住。

业务含义

操作工在工位上扫 SN + 工位码，系统判断“这个 SN 现在能不能过这道工序”。判断过程就是八条规则按顺序跑一遍，任何一条不过就拦截并告诉工人为什么（比如“顺序不对：请先过 RF 站”）。过了就记一条流水、把 SN 往前推一道工序。

页面：mes-tws-ui/src/views/exec/Simulator.vue（过站模拟器）点「提交过站」
→ axios：src/api/exec.js checkin → POST /api/station/checkin（动态表单按规则渲染测试项/绑定/上料提示，来自 GET /api/station/context）
→ Controller：ExecutionController.checkin(CheckinDTO)
→ Service：CheckinService.checkin() @Transactional
→ ① 工位码→工序、SN→工单→快照工序（再看第③步，这里查的是 plan_wo_operation）
→ ② 加 Redis 锁（防双击/重放）
→ ③ 跑 八规则链（按 order 顺序）
→ ④ 落 station_log + 推进 sn_registry（NG 自动开不良单）
→ ⑤ 发 StationCheckinEvent 异步更新工单数量

八规则链：策略列表 + order 排序 + for 循环（不是经典 next 指针）

重复过站的三道防线（面试必问）

① Redis 锁RedisLockService：key mes:lock:checkin:{sn}:{stationCode}，SET NX PX 5000（5 秒），Lua 脚本比对 token 再删。挡“双击/并发重放”。
② DuplicateRule查 station_log：同 SN+工位+轮次已 OK 计数>0 则拦。
③ 唯一索引station_log.checkin_key = sn:stationCode:retestRound，UNIQUE KEY uk_checkin_key。INSERT 触发 DuplicateKeyException → 兜底一切并发。

学完这一层你该记住：八规则是“策略列表按 order 跑 for 循环”，加新规则只需新增一个 Bean（零改主流程）。重复过站靠“Redis锁→查库→唯一索引”三道防线。过站只校验+落库，统计走异步（事件/MQ）。

业务 · 闭环

⑥ 维修回流闭环

过站 NG 会自动开不良单。维修员修好后，这台机器要能“流回”产线重测——而且重测不能污染良率口径。这就是闭环。

学完这一层你该记住：闭环 = “开单(OPEN) → 维修(REPAIRED/SCRAP) → 回流重测(RETEST, retest_round+1)”。维修结果通过 sn_registry 状态回流到工单/工序，且重测机不污染 FPY。

业务 · 指标

⑦ FPY 双口径 SQL

客户既要“一次直通率”（不含返修），又要“最终良率”（含返修）。两套口径都得算得清——靠一条 SQL 的左连接差异实现。

页面：mes-tws-ui/src/views/quality/FpyReport.vue（ECharts 双轴趋势+柏拉图）
→ axios：GET /api/fpy/summary、/api/fpy/daily、/api/fpy/pareto
→ Controller：QualityController.fpySummary/fpyDaily/fpyPareto
→ Service：FpyService.summary() / daily() / pareto()
→ SQL：QualityStatMapper.fpyByWo（MyBatis @Select）

核心 SQL（真实存在）

-- QualityStatMapper.fpyByWo
SELECT w.id AS woId, w.wo_no AS woNo, w.plan_qty AS planQty,
  COUNT(s.id) AS finished,                              -- 已完工整机
  SUM(CASE WHEN bad.sn IS NULL THEN 1 ELSE 0 END) AS firstPass, -- 一次直通
  (SELECT COUNT(*) FROM sn_registry s2
     WHERE s2.work_order_id=w.id AND s2.sn_type='MACHINE' AND s2.status='SCRAP') AS scrapped
FROM sn_registry s
JOIN plan_work_order w ON w.id = s.work_order_id
LEFT JOIN (SELECT DISTINCT sn FROM station_log
             WHERE record_type='CHECKIN' AND (result='NG' OR retest_round > 0)) bad
  ON bad.sn = s.sn
WHERE s.sn_type='MACHINE' AND s.status='DONE'
GROUP BY w.id, w.wo_no, w.plan_qty ORDER BY w.id
口径公式含义怎么在 SQL 里区分
FPY 一次直通率firstPass / finished不含返修，反映“一次就做好”的能力bad 子查询命中“有过 NG 或 retest_round>0 的 SN”，从 finished 里剔掉
最终良率finished / (finished + scrapped)含返修，修好的也算良品只剔除 SCRAP 报废，retest_round>0 的修好机仍计入
为什么重测不污染 FPY？ 维修回流后的过站 retest_round>0，LEFT JOIN 子查询把它判为“非一次直通”，所以在分子 firstPass 里被排除 —— FPY 因此真实反映首过能力，而最终良率又把修好的算回来。

学完这一层你该记住：双口径 = 同一个 finished 分母，分子差一个“是否剔除 retest_round>0 / NG”。一条 LEFT JOIN 子查询同时服务两个指标。

业务 · 追溯

⑧ 正反向追溯

审厂要“一只耳机出问题，10 分钟查出它用了哪批麦克风、影响了哪些整机”。正向（SN→全档案）和反（批次→整机）都靠同一批索引表。

页面：mes-tws-ui/src/views/trace/TraceForward.vue（正向）、TraceReverse.vue（反向）
→ axios：GET /api/trace/forward/{sn}、GET /api/trace/reverse/{batchNo}、GET /api/trace/tasks
→ Controller：TraceController.forward() / reverse() / tasks()
→ Service：TraceService.forward(sn) / reverse(batchNo) / recentTasks() / saveTask()
→ 表：sn_registry / station_log / sn_binding / md_material_batch / defect_record / repair_record / trace_task
flowchart LR subgraph 正向 SN→全档案 F1[sn_registry 主档] --> F2[station_log 过站时间线] F1 --> F3[sn_binding 子件+批次] F1 --> F4[defect_record/repair_record] end subgraph 反向 批次→整机 R1[md_material_batch 批次] --> R2[sn_registry 部件SN] R2 --> R3[parent_sn 上溯整机] R3 --> R4[统计受影响整机清单] end
正向 forward(sn)取 sn_registry 主档 → 按 SN 查 station_log(CHECKIN/BINDING) 时间线 → 整机查 sn_binding 子件及 batch_no，部件查 parent_sn 父机 → 关联 defect/repair
反向 reverse(batchNo)凭 batch_no 查 sn_registry 部件 SN → 经 parent_sn 上溯到 MACHINE 整机，统计受影响数量
留痕每次追溯 saveTask 写 trace_task(task_no, trace_type, query_key, result_count, cost_ms) —— 直接替代“人工 2 天出报告”

学完这一层你该记住：正向和反向共享 sn_registry 的两个索引列 batch_no（承载批次）和 parent_sn（承载多级绑定）。一码到底，正反向穿透。

收尾 · 一条 SN 的旅程

把八步串成一条线：一只耳机的完整体验

现在你应该能把所有模块连起来了。下面这只 SN「MACHINE-0001」的一生，就是八步的串联：

sequenceDiagram participant 计划员 as 计划员(planner1) participant 系统 as MES后端 participant 操作工 as 工位(op1) participant 质量员 as 质检(qc1) 计划员->>系统: ①登录拿token → ②建物料 → ③发工艺路线v2 计划员->>系统: ④建工单(拍路线快照)+下达开工 操作工->>系统: ⑤过站:扫SN+工位 → 八规则链全过 → 写station_log Note over 系统: 三码绑定/上料也走同控制器 操作工->>系统: ⑤某站NG → 自动开defect_record(OPEN) 质量员->>系统: ⑥维修 → sn_registry=RETEST 操作工->>系统: ⑤回流重测(retest_round+1) → 过站 质量员->>系统: ⑦看FPY双口径(返修机不污染FPY) 客户审厂->>系统: ⑧正向查SN全档案 / 反向查问题批次影响整机
这条线就是你的“简历主线”：工单驱动 → 现场执行（过站八规则）→ 质量拦截（维修回流）→ 追溯闭环。每一环都能展开成上面的某一节。
